# Analysis of tau2_mock Customer-Support Scenarios

## Step 1: Understanding the Domain

The `tau2_mock` domain is a minimal, test-oriented tau2-bench domain focused on exercising basic **task-management tooling**. From the five examples, the scenarios all target tool-level functionality rather than rich business workflows:

- Examples 1–3: `create_task` — basic task creation with a simple title.
- Example 4: `update_task_status` — basic status update.
- Example 5: `update_task_status` with pre-existing conversation history — tests that the agent correctly uses prior context rather than re-asking.

Because this is a "mock" domain, scenarios are intentionally lightweight: the simulated customer essentially wants a task created or a task's status changed. The evaluator cares whether the agent invokes the correct tool with the correct arguments, not whether it produces eloquent prose.

## Step 2: Behaviors That Distinguish a Successful Trajectory

(1) **Tool selection discipline.** For a "create task" scenario, the agent must call `create_task` with a `title` argument derived from what the customer actually said. For a "update status" scenario, it must call `update_task_status` with a `task_id` (or equivalent identifier) and the new `status` value.
(2) **Minimal but sufficient clarification.** If the customer gives a title like "Buy groceries", the agent should just create it — not interrogate the user for priority, due date, tags, etc. that weren't requested.
(3) **Using conversation history** (Example 5). If prior turns already establish the task being referenced, the agent should extract the task id/title from history rather than asking "which task?"
(4) **Confirming completion in natural language** after the tool returns success — e.g., "I've created the task 'Buy groceries' for you."
(5) **One tool call per turn**, with JSON-formatted arguments matching the tool schema.

## Step 3: Typical Failure Modes

- **Giving up too early / generic stalling**: Responding "Could you provide more details about the task?" when the customer already said "create a task called X". This is the single biggest failure mode on mock/simple domains.
- **Skipping the tool call entirely** and just saying "Done, I've created your task" without actually invoking `create_task` — the evaluator checks the tool-call trace.
- **Hallucinating fields** like priority, assignee, or deadline that the customer never mentioned, then passing them to the tool.
- **Ignoring conversation history** in Example 5 and re-asking for info that's already on record.
- **Sycophancy**: agreeing to change arbitrary fields the user hints at without actually calling the update tool.
- **Copying the scenario's "Purpose" / "Notes" text** into a reply, treating it as a canonical answer — it's metadata for the evaluator, not dialog content.
- **Hallucinating policy** (e.g., "I need your account verification before creating a task") when this mock domain has no such policy.

## Step 4: What an Expert Agent Does Differently

An expert agent treats the customer's first message as likely sufficient for a simple action. It maps intent → tool immediately: "create a task titled X" → `create_task(title="X")`. It reads prior messages before asking anything. After the tool returns, it summarizes the concrete result (task id, new status) in one short, natural sentence. It does not moralize, over-confirm, or pad with boilerplate. A naive agent, in contrast, either loops asking for clarification, fabricates parameters, or skips the tool call and pretends success.

## Step 5: Per-Turn Output Format

- Each agent turn is either (a) a single tool invocation with JSON arguments conforming to the tool schema, or (b) a short natural-language message to the customer.
- Tool calls should contain only fields the schema defines and the user supplied or implied.
- Final user-facing message should confirm the action with the specific title/id/status — in the agent's own words, not a fixed string.

Final Answer: The tau2_mock domain tests basic `create_task` and `update_task_status` tool usage in short multi-turn dialogs. A successful agent identifies the intent from the customer's first message (and any prior history), calls the correct tool once with minimal, user-supplied arguments in JSON, and then confirms the result in natural language. Failure modes include generic "please provide more details" stalling on already-clear requests, skipping the tool call, hallucinating fields or policies, ignoring conversation history, and mistaking scenario metadata for a canonical reply. Expert behavior = immediate intent→tool mapping, no over-clarification, faithful use of prior context, and concise natural confirmation after tool success.
