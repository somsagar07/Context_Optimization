# Analysis of tau2_telecom Customer Support Scenarios

## (1) Scenario Types in This Domain

The examples all focus on **Mobile Data / Slow Internet Issues** — a common telecom troubleshooting path. The customer (John Smith, 555-123-2002) reports that mobile data either stops working or is very slow, and insists on "excellent" speed-test results. Key scenario variables include: **location context** (at home in the US vs. abroad in France — which triggers different policy paths around roaming), **willingness to refuel data** (2.0 GB yes, plan change no), and **strict success criteria** (only "excellent" counts as resolved). More broadly, the telecom domain covers issues like MMS/SMS failures, call-drop problems, billing/refund disputes, plan changes, line suspensions, and device-specific diagnostics — each requiring its own tool sequence.

## (2) Behaviors That Define a Successful Trajectory

A successful agent should:
- **Authenticate the customer first** (look up the line by phone number; verify identity per policy before making account changes).
- **Call diagnostic tools systematically**: `get_status_bar`, `get_line_status`, `can_send_mms`, `run_speed_test`, check APN settings, check roaming status, check data usage vs. plan limit.
- **Differentiate root causes based on context**: if the customer is abroad in France, check whether an international roaming add-on is enabled — that's likely the root cause, not a local signal issue. If at home, check whether the data allotment has been exceeded (triggering throttling) — resolution is a data refuel.
- **Apply the customer's stated constraints**: the user allows up to 2.0 GB refuel but refuses plan changes — so the agent must not propose a plan upgrade.
- **Loop the diagnostic until the speed test actually returns "excellent"**: run remedy → re-run speed test → narrate result → iterate. Don't declare victory on "good".
- **Refuse/defer out-of-policy actions** (e.g., free credits not justified, plan changes the customer rejected).

## (3) Typical Failure Modes

- **Giving up too early** by asking vague questions like "Can you provide more details about the issue?" instead of calling a diagnostic tool. The customer's scenario already says mobile data is slow — the agent should *act*, not re-interview.
- **Sycophancy**: accepting a "good" speed-test result as resolved when the customer explicitly requires "excellent".
- **Skipping verification**: not confirming phone number / identity before making changes; not re-running the speed test after a remedy.
- **Hallucinating policy** — inventing refund amounts, making up plan features, or claiming roaming is included when the tools say otherwise.
- **Ignoring context** — running the same US-centric playbook when the customer is abroad, missing that roaming add-on is the real issue.
- **Copying placeholder strings** or outputting canonical directives instead of having a natural, tool-grounded conversation.
- **Batching multiple tool calls into one turn** when the interface expects one per turn, or malformed JSON arguments.

## (4) Expert vs. Naive Agent

An **expert** agent reads the location signal ("abroad in France" vs. "at home"), hypothesizes the likely root cause before acting (roaming not provisioned vs. data cap exhausted), calls the minimal diagnostic tools to confirm, applies the targeted fix (enable roaming pass / refuel 2.0 GB), then **re-runs the speed test** and only closes the ticket when it returns "excellent". The expert narrates findings plainly ("I see your data is throttled because you're over your monthly cap") and respects customer constraints.

A **naive** agent asks open-ended questions, suggests generic reboots without checking status first, accepts partial improvements, proposes plan upgrades the customer refused, or claims resolution without verifying.

## (5) Per-Turn Output Format

Each agent turn is either a **natural-language message** to the customer or a **single tool call** with structured JSON arguments (e.g., `run_speed_test({"phone_number": "555-123-2002"})`). Tool results are observations the agent must ground its next reply on — never fabricate. There is **no canonical final string**; the dialog ends when the customer confirms resolution or the agent properly transfers/refuses per policy.

Final Answer: The tau2_telecom scenarios are multi-turn mobile-data troubleshooting dialogs where a successful agent authenticates the caller, runs context-appropriate diagnostic tools (status bar, line status, speed test, roaming/data-cap checks), applies a targeted remedy consistent with the customer's stated constraints (e.g., refuel up to 2.0 GB but no plan change), and iterates until the speed test returns "excellent" — differentiating root causes by location (roaming provisioning abroad vs. data-cap throttling at home); failure modes include giving up with generic "please provide more details" prompts, accepting "good" as resolved (sycophancy), skipping verification, hallucinating policy, ignoring the abroad-vs-home distinction, and outputting canonical/placeholder strings instead of conversing with grounded tool calls (one per turn, JSON args).
